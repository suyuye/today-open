第一部分：产品设计

1. 产品概述

今日营业中是一款免费、开源的 Windows 桌面便签软件，主打 "轻量、快速、有温度" 的便签体验。

核心功能

  • 桌面便签：随时记录，自动保存
  • 置顶不抢焦点：便签常驻桌面不打扰工作
  • 折叠与锁定：折叠节省空间，锁定防止误触
  • 透明度调节：半透明便签温柔融入桌面
  • 十二种便签色：米黄 / 薄荷绿 / 雾霾蓝 / 豆沙粉 / 紫罗兰 / 高级灰，每色相含深浅两档
  • 纸张质感：微纸纤维 + 顶部光照 + 纸边厚度，三种半透明叠加
  • 待办事项：轻量 Markdown 语法（- [ ] / - [x]），自绘复选框
  • 提醒服务：单次 / 每日 / 每周 / 工作日 / 每月
  • 标签分类：给便签打上标签，灵活整理归档
  • 信件管理面板：搜索、筛选、批量管理所有便签
  • 图片附件（v1.3.0）：粘贴 / 选择图片入库，缩略图条展示，随备份自动走
  • 贴边收纳（v1.4.0）：拖到屏幕边缘收成细条，悬停唤出（默认关闭，按便签开启）
  • 卷角（v1.5.1）：右下角折起一小块，颜色从便签自身推出（默认关闭）
  • 数据导入（v1.2.0）：JSON / Markdown / 文本导回，按颜色 / 标签 / 时间筛选，搜索关键词高亮
  • 系统托盘：最小化到托盘，不占任务栏空间
  • 全局快捷键：一键新建，随时唤出
  • 开机自启：可选设置
  • 极简模式：桌面磁贴显示

设计风格

现代纸张融合风 — 便签本体用莫兰迪色 + 微纸质感，控制面板用浅色纯色背景（原计划 Mica 材质，因 WPF 兼容性问题放弃）。

v1.1.1 补充：便签的"纸感"从早期规划的"纯色块"演进为纯 WPF 绘制的三层质感叠加。之所以不用系统材质，见 §11.10 纸张质感实现。

2. 设计原则

原则 说明
输入即保存 没有保存按钮，打字自动落库，降低认知负担
常驻不打扰 置顶但不抢焦点，悬停才显示控制按钮，默认界面干净
操作可撤销 删除走回收站，误删可恢复；所有设置即时生效
纸张温度感 便签本体保留便利贴的隐喻：柔和色彩、微纸质感、圆角
系统一致性 控制面板、列表、设置页使用浅色纯色背景，和 Windows 11 视觉风格协调
键盘优先 常用操作都有快捷键，鼠标是补充
色彩自洽 与便签相关的所有颜色都从便签自身的色板取值，不引入无关色相

v1.1.1 补充「色彩自洽」原则：这条原则是从两次翻车里总结出来的 —— ① 便签阴影原本用纯黑，压在彩色纸上会让边缘发脏灰 → 改为跟色相的暖色阴影； ② 折叠态待办徽标原本用品牌橙 #E8743B，与便签配色无关，视觉上像"外来的通知"。 凡是长在便签上的元素，颜色都应当能从这张便签自己身上找到出处。

色彩系统实现约束：

  • 色板列表只有一处真源：Helpers/NoteColorHelper.cs 的 All。 便签"更多"菜单、编辑区改色、批量改色、设置页默认色、标签弹窗全部从它取值。 新增颜色只需改 Colors.xaml + NoteColor 枚举，其余地方零改动。
  • 颜色存库是枚举名小写（ToLowerInvariant()）。读取必须走 NoteColorHelper.Parse()（内含旧名映射 Yellow → YellowDeep 等 + 兜底默认）， 不要直接 Enum.Parse<NoteColor> —— 否则改枚举名会让所有旧便签读不出颜色 （会直接抛异常，不是静默降级）。
  • 浅档统一规律：Bg 比深档亮、Border 更淡、Text 比深档浅一点点以保持对比。

折叠态设计（v1.1.1 完善）

折叠后便签变成完整圆角胶囊形，上下圆角一致。折叠态要额外承担两个信息职责：

元素 作用 实现
语义色脊 折叠后底色被标题栏色取代，便签"是什么颜色"的信息会丢失 左侧 3px 竖条（RadiusX/Y=1.5，Margin=6,7），填充 NoteAccentBrush（= Border 色）
待办徽标 折叠后看不到内容，这是唯一的进度提示 见下方说明

为什么色脊用 Border 色而不是 Bg 色：折叠胶囊的底色已经是"标题栏色"， 若色脊再用 Bg 色，会与胶囊底色出现色差、显得脏。用 Border 色既守住颜色身份， 又像"书脊"一样给出「这是一张便签」的暗示。

展开态不需要色脊（那时四周都有便签底色），故仅折叠时可见。

待办徽标（折叠态未完成计数）：

  • 数据源：UncheckedTodoCount（只统计未完成项；全部完成时不显示，避免挂个 0 碍眼）
  • 可见性绑定：TodoBadgeVisibility
  • 刷新时机：勾选待办时通过 INoteLineParent.NotifyTodoStateChanged() 刷新， 与 NotifyLineContentChanged() 职责分开 —— 勾选待办不该触发内容保存。

锁定态设计（v1.1.1 完善）

锁定态的斜纹浓度定在 7%（3% 时肉眼几乎不可见）。

关键设计约束：必须同时给出"可读的说明 + 可退出的入口"（提示条 + 解锁按钮）， 否则用户分不清"被锁住了"和"界面坏了"。

8.3 数据库迁移机制

应用启动时执行 幂等的增量迁移：AppDbContext.MigrateSchema(connection) 每次启动都检查， 用 PRAGMA table_info({table}) 判断列是否存在，缺列则 ALTER TABLE ADD COLUMN。

private static void MigrateSchema(SqliteConnection connection)
{
    if (!ColumnExists(connection, "Notes", "Title"))         { /* ALTER TABLE Notes ADD COLUMN Title TEXT */ }
    if (!ColumnExists(connection, "Notes", "IsMinimal"))     { /* ... INTEGER NOT NULL DEFAULT 0 */ }
    if (!ColumnExists(connection, "Notes", "IsDockEnabled")) { /* ... INTEGER NOT NULL DEFAULT 0（v1.4.0） */ }
    if (!ColumnExists(connection, "Notes", "DockEdge"))      { /* ... INTEGER NOT NULL DEFAULT 0（v1.4.0） */ }
    if (!ColumnExists(connection, "Notes", "IsDogEar"))      { /* ... INTEGER NOT NULL DEFAULT 0（v1.5.1） */ }
}

设计要点：新建表的 SQL 里直接包含全部列，旧库通过迁移补列 —— 两条路径都能得到相同的结构。 新增字段时只需在这里加一个 if 分支，同时更新建表 SQL 与 NoteRepository 的列清单。

ColumnExists 读取 PRAGMA table_info 的索引 1（name）， 注意该结果集的列顺序是 cid(0), name(1), type(2), notnull(3), dflt_value(4), pk(5)。

11.10 跨行选区编辑器（核心）

这是本项目技术上最独特、也最容易踩坑的部分，改动前务必读完本节。

架构：为什么不用原生 SelectionLength

便签正文是多行的（ItemsControl 按行渲染，每行一个独立 TextBox）， 但用户期望的是跨行的连续选区（像在 Word 里拖选一样）。

WPF 的 TextBox 的选区（SelectionStart / SelectionLength）只能存在于单个 TextBox 内部， 无法跨越控件。因此本项目的做法是：

选区状态由编辑器自己持有（_anchor / _focus 两个 (int Line, int Caret)? 元组）， 高亮由 Adorner（SelectionAdorner）自绘，各行 TextBox 的 SelectionLength 始终是 0。

// 选区状态存放在编辑器自身，不在任何 TextBox 里
private (int Line, int Caret)? _anchor;   // 起点
private (int Line, int Caret)? _focus;    // 终点（可位于 anchor 前后）

这个架构带来两个必须牢记的后果：

  1. 系统命令"看不见"这个选区（详见下一节）
  2. 绘制性能必须自己优化（详见"性能修复"）

陷阱一：Ctrl+C / Ctrl+X 完全无反应

症状：跨行选中多行后按 Ctrl+C，剪贴板只有最后一行；Ctrl+X 完全没反应。

根因（双层缺陷）：

① 命令路由根本不派发。 CommandManager 在命令 CanExecute == false 时，不会派发 Executed， 因此 PreviewExecuted 拦截器永远不会被调用。 而 TextBox 的 Copy / Cut 的 CanExecute 只认它自己的 SelectionLength —— 跨行选区存在 _anchor / _focus 里，各行 TextBox 的 SelectionLength 全是 0， 所以对命令系统完全不可见 → 命令被判定为"不可执行" → 表现为按键无反应。

对照证据：Ctrl+A 一直是好的，因为 SelectAll.CanExecute 恒为 true，不走这个门槛。 实测日志里 Ctrl+A 有 PreviewExecuted 记录，Ctrl+C / Ctrl+X 完全没有。

② Ctrl+C 的键位映射会走到 Insert 键（Ctrl+Insert 是 Copy 的另一条键路）， 说明命令路由本身也不可靠。

修复：把 Ctrl+C / X / A / V 从"命令路由"改为在 PreviewKeyDown 里直接处理：

// Ctrl+C / Ctrl+X / Ctrl+A / Ctrl+V：直接在本层处理，不依赖命令路由
if (isCtrl && !e.IsRepeat)
{
    switch (e.Key)
    {
        case Key.C:
            e.Handled = true;
            if (HasSelection())              { CopySelection(); }
            else if (box.SelectionLength > 0) { box.Copy(); }
            return;
        case Key.X:
            e.Handled = true;
            if (_host.IsReadOnly) return;
            if (HasSelection())              { CopySelection(); DeleteSelection(); }
            else if (box.SelectionLength > 0) { box.Cut(); }
            return;
        case Key.A:
            e.Handled = true;
            SelectAll();
            return;
        case Key.V:
            e.Handled = true;
            if (_host.IsReadOnly) return;
            PasteInto(box);
            return;
    }
}

保留 PreviewExecuted 兜底的命令（它们不受选区长度限制，且能兜住右键菜单入口）：

private void OnLinePreviewExecuted(object sender, ExecutedRoutedEventArgs e)
{
    if (sender is not TextBox box) return;
    if (e.Command == ApplicationCommands.Paste)      { e.Handled = true; PasteInto(box); }
    else if (e.Command == ApplicationCommands.SelectAll) { e.Handled = true; SelectAll(); }
    else if (e.Command == ApplicationCommands.Copy && HasSelection())   { e.Handled = true; CopySelection(); }
    else if (e.Command == ApplicationCommands.Cut  && HasSelection())   { e.Handled = true; CutFocused(); }
    else if (e.Command == ApplicationCommands.Delete && HasSelection()) { e.Handled = true; if (!_host.IsReadOnly) DeleteSelection(); }
}

⚠️ 强行记住这条规则：编辑区的 Ctrl+C/X/A/V 不要改回命令路由拦截。 现状是"键路（PreviewKeyDown）为主 + 命令路（PreviewExecuted）兜底"。

编辑区完整键位表：

键位 行为 处理层

Ctrl+X 剪切跨行选区 PreviewKeyDown

陷阱二：选中文字时界面卡死

症状：在编辑区拖选文字时卡顿，整个软件跟着无响应，松开鼠标后仍不恢复。

根因：SelectionAdorner 原实现在 LayoutUpdated 里无条件 InvalidateVisual()。 LayoutUpdated 每个布局周期（含纯渲染周期）都会触发，而 InvalidateVisual() 会再次引发布局 → 形成 "重绘 → 布局 → 再重绘" 的自激循环。 且 OnRender 内还在做 GetRectFromCharacterIndex 逐字符几何计算，进一步放大开销。

实测数据（受控 A/B，中位数，取 UI 线程占用）：

空闲 拖选 松手后静置
修复前 3.9% 133.9% 101.3%
修复后 4.3% 52% 3.6%

修复要点（4 条，缺一不可）：

  1. SetRanges 里预先算好矩形存入 _cachedRects，OnRender 只做 DrawRectangle
  2. 逐字符矩形按 TextBox 缓存（SelectionGeometryCache._charRects）， 失效键为 TextLength / FontSize / ActualWidth
  3. 无选区时完全不触碰装饰器（SetRanges(null) 会强制 InvalidateVisual）
  4. 加入端点指纹（SameRanges），选区端点未变时直接复用 _rects， 拖动只重算受影响的少数几行

陷阱三：行尾最后一个字选不上

这是同一处代码的两个独立 bug，都属于"缓存优化引入的回归"：

bug A：每段最后一个字选不上（从前往后拖选也选不上）

  • 根因：为做缓存，把"行尾插入点"的矩形改成了手工拼接（末字符右移）， 拼出来的矩形宽度为 0，导致选区终点落在行尾时算不出可见高亮， 该行选的选区长度被判定为 0。
  • 修复：改回由原生接口 box.GetRectFromCharacterIndex(len) 取行尾插入点矩形 （取不到时才用 MeasureSpaceWidth 测出的字宽兜底），并修正右边界取值方式。
// 行尾插入点：优先用原生查询，取不到时再退回「末字符右移」的保守近似，并保证高度非零
var tail = box.GetRectFromCharacterIndex(len);
if (tail.Height <= 0 && tail.Width <= 0)
{
    var last = len > 0 ? arr[len - 1] : new Rect(0, 0, 0, box.ActualHeight);
    var h = last.Height > 0 ? last.Height : box.ActualHeight;
    var w = MeasureSpaceWidth(box);   // 用一个空文本测量出的字宽，避免零宽矩形
    tail = new Rect(last.Right, last.Top, w, h);
}
arr[len] = tail;

bug B：从后往前拖选时，行尾最后一个字仍选不中

  • 根因：GetCharacterIndexFromPoint 在文本右侧的空白处 永远不会返回"行尾位置"（最多给出最后一个字的索引）， 而旧代码只在这个接口返回失败时才回退到行尾。于是：
    • 从前往后拖选时，光标会落到下一行行首，行尾由整行补全 → 看不出问题
    • 从后往前拖选时，上一行的末端必须正好等于"行尾位置" → 这个位置永远取不到，导致该行最后一个字始终漏选
  • 修复：先取"行尾插入点"的实际坐标，指针越过该点即判定为行尾， 不再依赖系统接口的返回值。

选区矩形生成逻辑（支持自动换行）

按视觉行分段：逐字符遍历，用 r.Top > top + 0.5 判断是否换行， 换行时先把上一视觉行收尾（右端取上一字符的右边缘），再以新行起点继续。

for (var i = s + 1; i <= e; i++)
{
    var r = CharRectAt(charRects, i);
    if (r.Top > top + 0.5)
    {
        // 换行：先把上一视觉行收尾，右端为上一字符的右边缘
        AddRow(rects, matrix, x0, CharRectAt(charRects, i - 1).Right, top, height);
        top = r.Top; height = r.Height > 0 ? r.Height : height; x0 = r.Left;
    }
    x1 = r.Left;
}
if (x1 <= x0) x1 = CharRectAt(charRects, e).Right;
AddRow(rects, matrix, x0, x1, top, height);

右端取值规则：取"e 位置插入点矩形的左边缘"，当 e == len 时那正是 最后一字的右边缘，因此行尾字符也能被完整高亮。

AddRow 里的可见性判断用极小容差 x1 - x0 <= 0.01， 避免浮点舍入把行尾一个像素的行吞掉。

坐标系与变换

行的 TextBox 相对装饰器可能有位移与缩放，因此矩形需经变换矩阵映射。 注意 TransformToVisual 的静态返回类型是 GeneralTransform（无 .Value 属性）， 实际运行时对象是 MatrixTransform，必须用模式匹配取矩阵：

if (box.TransformToVisual(adorner) is not MatrixTransform matrixTransform) continue;
var matrix = matrixTransform.Matrix;
// 变换在本场景下是「平移 + 等比缩放」，宽度缩放等于对角线缩放 m11

11.11 纸张质感实现（纯 WPF 绘制）

为什么不用 Mica / Acrylic

便签窗口用不了系统材质，这是架构级的限制：

  1. 便签窗口用了 AllowsTransparency=True（分层窗口），与 DWM 系统背景材质互斥
  2. 系统材质在 Windows 10 上不可用

因此改用纯 WPF 绘制方案，在 Win10 / Win11 表现完全一致，零兼容风险。

三层叠加

在便签底层叠加三个半透明画刷，因此能跟 12 种便签底色自然融合， 不需要为每种颜色各配一套纹理：

画刷 作用 关键参数
PaperFiberBrush 纸纤维（极淡的不规则短划线平铺） 24×24 tile，三档浓度 #08 / #0A / #0C，整体 Opacity=0.5
PaperLightBrush 上方光照（顶部一点暖白，往下 120px 内淡出） #14FFFFFF → #06FFFFFF
纸边厚度渐变 纸边厚度感 线性渐变

⚠️ 最大的技术教训：小尺寸 tile 会产生可见网格

早先试过 6×6 的 tile，肉眼能看到规则网格，像"布纹/网纱"而不是纸。

量化定位过程（用水平自相关函数测周期性）：

6×6 tile  → 自相关在 lag=18（即 6 的整数倍）出现 0.98 的强峰
24×24 tile + 短划线全部偏离网格交点 + 三档浓度（#08/#0A/#0C）互相错开
          → 自相关峰值 lag=2 → 0.81，之后平滑衰减，无次级峰

结论：纹理类视觉参数不要靠肉眼判断。 用自相关函数测周期性（有无次级峰），用亮度标准差测强度（会不会太脏）， 一次就能定位。

强度基线（参考值）：纸纤维纹理亮度极差 6~7（量程 255）、sd ≈ 0.9。 正常距离下只表现为"纸面不光滑"，看清了就说明做脏了。

密度刻意做得很低

纤维只画 1.5% 左右的黑。密度做了三档错开，避免所有纤维同等强度 而产生"花纹"的规整感。

22. 常见问题与解决方案

22.1 开发环境问题

Q: 卡巴斯基拦截 AI 工具的 PowerShell 命令

现象：卡巴斯基报 HEUR:Trojan-Downloader.PowerShell.Bitser.gen，拦截 AI 工具执行的 PowerShell 命令。

解决方案：将以下目录加入卡巴斯基排除项：

  • %TEMP%\ai\（AI 工具临时目录）
  • D:\PJ\Note\（项目目录）
  • %APPDATA%\今日营业中\（软件数据目录）

Q: 编译时报 CS0118 错误（Note 被解析成命名空间）

现象：项目改名 Note.App 后，根命名空间第一段 Note 与模型类 Note 同名，导致 36 个 CS0118 错误。

解决方案：根命名空间改为单段 NoteApp，程序集名保持 Note.App，模型 Note 保持原名。

Q: dotnet build 报「成功」但根本没重新编译

现象：改完 XAML 后 dotnet build -c Release 报 0 错误，但截图效果与改前逐字节相同。

根本原因：带 -r 与不带 -r 走不同的 obj 子目录 （obj/Release/net10.0-windows/ vs obj/Release/net10.0-windows/win-x64/）， 增量构建判定"无变化"直接跳过。

解决方案：加 --no-incremental 强制全量重建；或删掉 obj 对应子目录。

教训：改完 XAML / C# 要看产物时间戳（Note.App.dll 的 mtime 是否晚于源文件），不要只信"0 错误"。

Q: TransformToVisual 报错找不到 Value 属性（CS1061）

现象：NoteLineEditor.cs 报 CS1061：GeneralTransform 未包含 Value。

原因：box.TransformToVisual(...) 的静态返回类型是 GeneralTransform（没有 .Value）， 实际运行时对象是 MatrixTransform。

解决方案：用模式匹配取矩阵。

if (transform is not MatrixTransform matrixTransform) { continue; }
drawingContext.PushTransform(new MatrixTransform(matrixTransform.Matrix));

22.2 运行时问题

Q: 便签窗口有黑边 / 方角

现象：使用 WindowChrome 后，便签窗口出现黑边或方角，系统按钮消失。

解决方案：改用 AllowsTransparency=True + WindowStyle=None，用 XAML CornerRadius + Clip 实现圆角。

Q: 列表面板标题栏选中时变黑

现象：列表面板窗口被选中时，标题栏呈现黑色，未选中时正常浅色。

解决方案：使用 DwmSetWindowAttribute Win32 API 设置标题栏背景色（DWMWA_CAPTION_COLOR=35）和文字色（DWMWA_TEXT_COLOR=36），封装为 TitleBarColorHelper.ApplyByCurrentTheme()。

Q: 深色模式下标题栏不跟随主题

现象：切换到深色模式后，列表面板和设置窗口内容已变深色，但标题栏仍为浅色。

解决方案：

  1. IThemeService 添加 ThemeChanged 事件
  2. ThemeService.ApplyTheme 触发事件
  3. TitleBarColorHelper.ApplyByCurrentTheme() 自动检测当前主题（通过 BgPage 颜色 R 值判断），浅色用 #F3F0EA + #1A1B1C，深色用 #1E1E1E + #E0E0E0
  4. NoteListView 和 SettingsWindow 订阅 ThemeChanged 事件实时更新

Q: 新建便签时列表重复显示

现象：新建便签会在中间的展示页面生成两个相同的便签，但左侧分类数量正确。

解决方案：三重保护

  1. _isNoteCreating 标志：新建便签期间抑制事件触发的刷新，结束后统一刷新一次
  2. _isReloading 标志：防止 ReloadNotes() 递归调用
  3. HashSet<Guid> 去重：同一个 Note.Id 只添加一次

Q: 窗口最大化最小化关闭按钮消失

现象：修改窗口样式后，窗口上的最大化最小化关闭等按钮没有了。

解决方案：不要使用 WindowChrome，改用 WindowStyle="SingleBorderWindow" + DwmSetWindowAttribute 改标题栏色，保留系统按钮。

Q: 🔴 编辑区 Ctrl+C 只能复制一行、Ctrl+X 完全无反应（v1.1.1 已修复）

现象：跨行选中 4 行文字后按 Ctrl+C，剪贴板只有最后一行；Ctrl+X 完全没反应。

根本原因（双层缺陷）：

  1. CommandManager 在命令 CanExecute == false 时不派发 Executed， 所以 PreviewExecuted 拦截器永远不会被调用。而 TextBox 的 Copy / Cut 的 CanExecute 只认它自己的 SelectionLength —— 跨行选区存在 _anchor / _focus 里， 各行 TextBox 的 SelectionLength 全是 0，对命令系统完全不可见。
  2. Ctrl+C 的键位映射会走到 Insert 键，命令路由本身也不可靠。

解决方案：把 Ctrl+C / X / A / V 改为在 PreviewKeyDown 里直接处理，不依赖命令路由。 详见 §11.10。

回归验证：拖选 4 行复制/剪切均能完整取得 4 行；Ctrl+A 全选复制内容逐字一致； 剪切后原内容真实减少；粘贴多行正常写入；Ctrl+Z / Ctrl+Y 未受影响。

Q: 🔴 在编辑区选中文字就卡死（v1.1.1 已修复）

现象：光标选中文字时卡顿，整个软件跟着卡死，松开鼠标后仍不恢复。

根本原因：选区高亮装饰器在 LayoutUpdated 里无条件 InvalidateVisual()， 形成"重绘 → 布局 → 再重绘"的自激循环，UI 线程被持续占满。 实测单线程长期跑在 100%，松手后仍有 101.3%。

解决方案：见 §11.10「陷阱二」，四条修复缺一不可。 修复后松手静置降至 3.6%。

Q: 🔴 无法选中每一段中的最后一个字（v1.1.1 已修复）

现象：拖选时每段的最后一个字选不上；后续发现从后往前拖选时更明显。

根本原因：这是两个独立 bug：

  1. 「行尾插入点」矩形被手工拼接成零宽，导致行尾选区长度被判定为 0
  2. GetCharacterIndexFromPoint 在文本右侧空白处永远不返回"行尾位置"， 而旧代码只在它失败时才回退到行尾

解决方案：见 §11.10「陷阱三」。 关键是行尾插入点必须交给原生接口取，不能用末字符矩形手工拼接。

Q: 🔴 软件启动后便签窗口一个都不出现（数据看起来"空了"）

现象：应用能启动，但桌面上一个便签窗口都没有，像是数据全丢了。

两个可能原因：

① 数据库时间戳格式错误（真实踩过）：CreatedAt / UpdatedAt 被写成毫秒整数 （如 1790069038632），DateTimeHelper.Parse 抛 FormatException → GetAllNotes 整体失败 → RestoreNoteWindows 失败。 改回 ISO 字符串即可（如 2026-09-22T17:23:58）。

② 单实例竞争（调试时常见）：上一个进程还没退干净（OnExit 要写库 + 释放 Mutex）， 新实例被单实例逻辑挡掉。等进程真正退出再额外等 3 秒再启新实例。

排查顺序建议：先看日志有没有 FormatException；再看是不是自己刚 kill 过进程。 不要一上来就怀疑数据被删了。

Q: 锁定便签后用户以为"界面坏了"

现象：便签被锁定后，用户分不清是被锁了还是软件出问题。

解决方案：锁定态必须同时给出"可读的说明 + 可退出的入口"（提示条 + 解锁按钮）， 且斜纹浓度定在 7%（3% 时肉眼几乎不可见）。

22.3 打包发布问题

Q: 便携版启动时被 Windows 拦截（错误代码 4551）

现象：在其他电脑上测试时，便携版或安装包被 Windows 拦截，报错"应用程序控制策略已阻止此文件"，错误代码 4551。

原因：Windows 11 智能应用控制（Smart App Control，SAC）拦截了未签名的新软件。

解决方案（按推荐顺序）：

  1. 解除文件锁定：右键安装包 → 属性 → 勾选"解除锁定" → 应用 → 确定
  2. 关闭 SAC：设置 → 隐私和安全 → Windows 安全中心 → 应用和浏览器控制 → 智能应用控制设置 → 关闭（注意：关闭后不可逆）
  3. 使用便携版：便携版比安装包更不容易被 SAC 拦截
  4. 代码签名：购买代码签名证书（Certum 开源证书约 100 元 / 年），对 exe 进行数字签名

Q: 为什么没有"更多信息→仍要运行"选项

现象：Windows 拦截提示只有"正常"按钮，没有"更多信息→仍要运行"选项。

原因：这是 Windows 11 智能应用控制（SAC）的拦截，不是 SmartScreen 拦截。SAC 更严格，没有"仍要运行"选项。

解决方案：见上方"错误代码 4551"的解决方案。

Q: 🔴 单文件版 exe 一启动就崩（DllNotFoundException）

现象：

Unhandled exception. System.DllNotFoundException: Dll was not found.
   at MS.Win32.UnsafeNativeMethods.CriticalSetWindowLong(...)
   at MS.Win32.HwndSubclass.HookWindowProc(...)

原因：发布命令漏了 -p:IncludeNativeLibrariesForSelfExtract=true， WPF 原生库（wpfgfx_cor3.dll 等）没被打进单文件。 产物体积会明显偏小（约 139 MB 而不是 149 MB）。

解决方案：补上该参数重新发布。

快速判定技巧：单文件版崩、非单文件版（bin/Release/.../win-x64/Note.App.exe）正常 → 100% 是这个参数漏了。

Q: 便携版没有重置便签信息，也没有欢迎便签

现象：便携版启动后显示之前测试的便签数据，没有欢迎便签。

原因：便签数据保存在 %APPDATA%\今日营业中\，不是程序目录。之前测试过这个软件，所以有数据残留。

解决方案：删除 %APPDATA%\今日营业中\ 目录，重新启动软件即可看到欢迎便签。

Q: 便携版如何彻底删除数据

详细步骤（五步）：

  1. 关闭软件：右键系统托盘图标 → 退出
  2. 删除软件文件夹：删除便携版所在目录
  3. 删除用户数据：文件资源管理器地址栏输入 %APPDATA%\今日营业中，删除整个文件夹（注意：会删除所有便签数据，无法恢复！）
  4. 删除注册表自启项（如开启过开机自启）：regedit → HKCU\Software\Microsoft\Windows\CurrentVersion\Run → 删除 TodayOpen 键值
  5. 删除桌面快捷方式（如创建过）

Q: Inno Setup 编译时报错找不到中文语言文件

现象：编译时报错 Couldn't open include file "ChineseSimplified.isl"。

原因：Inno Setup 安装时没有安装语言文件组件，Languages 目录为空。

解决方案：

  1. 注释掉脚本中的中文语言行，使用默认英文界面（不影响功能）
  2. 或手动下载 ChineseSimplified.isl 放到 C:\Program Files (x86)\Inno Setup 6\Languages\ 目录

Q: ZIP 中文文件名乱码

现象：用 Compress-Archive 打包的 ZIP，在某些解压软件中中文文件名乱码。

解决方案：改用 Python zipfile 或 .NET ZipFile.CreateFromDirectory 并指定 UTF-8 编码， 写入 arcname 时手动拼接中文名，不要用 PowerShell 的 Compress-Archive。

22.4 验证与测试问题（v1.1.1 新增）

本节记录在真实应用上做端到端验证时踩过的坑，供后续写验证脚本时参考。

Q: 🔴 验证脚本误操作用户的真实便签（代价最大的一条）

现象：为验证快捷键写的自动化脚本，把用户一条真实便签的内容清空了（发生过两次）。

根本原因：测试便签放在 PositionX=1500, Y=300，而用户一条真实便签在 PositionX=1501, Y=265 —— 屏幕位置几乎完全重合。脚本"取最靠某角窗口"的挑选逻辑误抓了用户的便签， 随后的 Ctrl+A + Ctrl+X 把它清空了。

防范规则：

  • 测试便签一律放屏幕左下空旷区（如 PositionX=200, PositionY=1400）
  • 挑选窗口用位置匹配，不要用尺寸匹配
  • 执行任何会修改内容的操作前，先复制一份数据库
  • 万一真清空了：从 today_open.db.bak_* 或 Backup\today_open_*.db 精确写回并回读逐字节校验，不要凭记忆重写

Q: 脚本按固定像素尺寸找不到便签窗口

现象：脚本按 500~620 的宽度范围匹配窗口，一个都匹配不到。

原因：本机屏幕 150% 缩放。数据库里 Width=520，屏幕上实际约 816； PositionX=1500 实际约 2250。按库里的数值匹配必然失败。

解决方案：不要按像素尺寸猜，改用 Windows UI Automation 拿控件的真实屏幕矩形：

import uiautomation as auto
win = auto.ControlFromHandle(hwnd)
# 遍历控件，取 ControlType == EditControl 的 BoundingRectangle

便签窗口内的控件结构（实测）：[0] 是标题框（更宽更靠上，约 1410×55）， [1]~[4] 才是正文 4 行（约 1374×41）。所以正文行 = boxes[1:]。

Q: 用 PostMessage 模拟按键在 WPF 上无效

现象：脚本发消息模拟鼠标拖选，应用毫无反应。

原因：WPF 不认 PostMessage 模拟的输入。

解决方案：用 SendInput 发真实鼠标/键盘事件（走 Windows 输入队列）， 这是驱动 WPF 应用做端到端验证的唯一可靠方式。

小坑：拖选起点用 ratio ≈ 0.02（最左）。用 0.12 会点得太靠右， 导致选区起点落在文字中间，表现为"剪贴板少了首字"。

Q: 用 subprocess.run(timeout=...) 验证 GUI 启动后查不到窗口

现象：subprocess.run(cmd, timeout=25) 超时后，后续查不到进程与窗口。

原因：超时后子进程被 kill 了。

解决方案：改用 subprocess.Popen + proc.poll() 轮询。 另外注意：对 GUI 程序，TimeoutExpired 本身反而是"正常运行"的信号（GUI 本来不退出）。

Q: Bash 里内联 python -c 的字符串被损坏

现象：python -c "...路径里有反斜杠或嵌套引号..." 报 SyntaxError: unterminated string literal。

原因：Git Bash 下嵌套引号 / 反斜杠会被转义损坏。

解决方案：写成独立的 .py 脚本文件再执行，不要内联复杂字符串。

22.5 AI 辅助开发问题

Q: 上下文太长怎么办

现象：对话上下文过长，AI 响应变慢或卡住。

解决方案：

  1. 每个 Phase 开始时新建对话
  2. 发前置指令说明项目背景和当前状态
  3. 让 AI 读取关键文件而不是把所有内容贴到对话里
  4. 上下文压缩后 AI 会丢失之前读取的文件内容，需要重新读取 —— 建议在前置指令中明确告诉 AI 需要读取哪些关键文件

Q: AI 生成的代码编译报错怎么办

解决方案：

  1. 把完整的报错信息贴给 AI
  2. 让 AI 读取报错的文件
  3. 让 AI 修复后重新编译
  4. 同一问题失败两次，换个思路或手动修复

Q: 修改 UI 后怎么确认改动真的生效了

不要只信"0 错误"。 两条硬性校验：

  1. 看产物时间戳：bin/Release/.../Note.App.dll 的 mtime 必须晚于最后改动的源文件
  2. 量化视觉参数（纹理 / 颜色类）：
    • 周期性（有没有可见网格）→ 用水平自相关，看有无次级峰
    • 强度（会不会太脏）→ 用亮度极差与标准差

参考基线：纸纤维纹理亮度极差 6~7（量程 255）、sd ≈ 0.9， 自相关在 lag ≥ 3 应平滑衰减到 0.5 以下、无次级峰。

24.4 Bug 修复记录

24.4.1 光标丢失问题

  • 问题描述：主页编辑区输入内容后，光标自动跳到最前面或丢失
  • 根本原因：
    1. 自动保存触发 NoteUpdated 事件 → NoteListViewModel.OnNoteChanged 调用 ReloadNotes() → Notes.Clear() 导致 SelectedNote 被临时设为 null → 编辑区被清空、焦点丢失
    2. 独立便签窗口的自动保存触发 UpdateNote() → 主页编辑区 OnNoteUpdated 被调用 → 内容略有不同 → 调用 RebuildLinesFromContent() → Lines 集合被重建 → TextBox 被重新创建 → 光标丢失
  • 修复方案：
    1. OnSelectedNoteChanged 中添加 _isReloading 检查，列表刷新期间不处理选中变化
    2. OnNoteUpdated 中添加 _isDirty 检查，用户正在编辑时不更新 EditableContent 和 Lines
    3. 添加 _isRebuildingLines 标志，防止重建行集合时触发无限循环

24.4.2 内容不同步问题

  • 问题描述：主页编辑区和独立便签窗口内容不同步
  • 根本原因：两个 ViewModel 的 OnNoteUpdated 方法都只同步了状态（置顶、锁定等），没有同步内容
  • 修复方案：
    1. NoteWindowViewModel.OnNoteUpdated：内容不同且不是本窗口自己保存时，同步 Note.Content 和 Content
    2. NotePreviewViewModel.OnNoteUpdated：内容不同且不是本编辑区自己保存时，同步 EditableTitle 和 EditableContent
    3. 两个地方都使用 _isSaving 标志，避免本窗口/编辑区自己保存时同步内容

24.4.3 Backspace 合并行问题

  • 问题描述：独立便签页面内容编辑时，按 Backspace 无法回到上一行
  • 根本原因：行 TextBox 的键盘事件使用 KeyDown（冒泡事件），被 TextBox 内部处理后才触发，无法拦截
  • 修复方案：将行 TextBox 的键盘事件从 KeyDown 改为 PreviewKeyDown（隧道事件），确保在 TextBox 内部处理之前拦截 Backspace 键

25.1 本轮改动的总体思路

优先级 问题 性质

25.2 交互与性能修复（重点）

25.2.1 编辑区选中文字卡死

症状：在内容编辑区拖选文字时卡顿，整个软件跟着无响应，松开鼠标后仍不恢复。

根因：选区高亮装饰器 SelectionAdorner 在 LayoutUpdated 里无条件调用 InvalidateVisual()。LayoutUpdated 每个布局周期（含纯渲染周期）都会触发， 而 InvalidateVisual() 会再次引发布局 → 形成 "重绘 → 布局 → 再重绘" 的自激循环； 且 OnRender 内还在做 GetRectFromCharacterIndex 逐字符几何计算，进一步放大开销。

实测（受控 A/B，中位数，UI 线程占用）：

空闲 拖选 松手后静置
修复前 3.9% 133.9% 101.3%
修复后 4.3% 52% 3.6%

修复要点（4 条，缺一不可）：

  1. SetRanges 里预先算好矩形存入 _cachedRects，OnRender 只做 DrawRectangle
  2. 逐字符矩形按 TextBox 缓存（SelectionGeometryCache._charRects）， 失效键为 TextLength / FontSize / ActualWidth
  3. 无选区时完全不触碰装饰器（SetRanges(null) 会强制 InvalidateVisual）
  4. 加入端点指纹（SameRanges），选区端点未变时直接复用 _rects， 拖动只重算受影响的少数几行

详见 §11.10。

25.2.2 无法选中每一段中的最后一个字

症状：拖选时每段最后一个字选不上；进一步测试发现从后往前拖选时更明显。

根因：这是两个独立 bug（都是缓存优化引入的回归）：

  1. 行尾插入点矩形被手工拼接成零宽：为做缓存，把行尾插入点改成"末字符右移"手工拼接， 拼出来的矩形宽度为 0，导致选区终点落在行尾时算不出可见高亮，选区长度被判定为 0。
  2. 系统接口在文本右侧空白处永不返回"行尾位置"： GetCharacterIndexFromPoint 在文本右侧空白处最多给出最后一个字的索引， 而旧代码只在它失败时才回退到行尾。于是从前往后拖选时（光标落到下一行行首、行尾由整行补全） 看不出问题，从后往前拖选时上一行末端永远取不到"行尾位置" → 始终漏选。

修复：

  • 行尾插入点改回由原生接口取（box.GetRectFromCharacterIndex(len)）， 取不到时才用 MeasureSpaceWidth 测出的字宽兜底，保证高度非零
  • 先取"行尾插入点"的实际坐标，指针越过该点即判定为行尾， 不再依赖系统接口的返回值

详见 §11.10。两项修复后「每段最后一个字」与 「从后往前拖选」均能正确选入。

25.2.3 Ctrl+X 无法剪切、Ctrl+C 只复制一行

症状：跨行选中 4 行后按 Ctrl+C，剪贴板只有最后一行；Ctrl+X 完全无反应。

根因（双层缺陷）：

  1. CommandManager 在命令 CanExecute == false 时不派发 Executed， 所以 PreviewExecuted 拦截器永远不会被调用。而 TextBox 的 Copy / Cut 的 CanExecute 只认它自己的 SelectionLength —— 跨行选区存在 _anchor / _focus 里，各行 TextBox 的 SelectionLength 全是 0， 对命令系统完全不可见 → 命令被判定为"不可执行" → 按键无反应。
  2. Ctrl+C 的键位映射会走到 Insert 键（Ctrl+Insert 是 Copy 的另一条键路）， 命令路由本身也不可靠。

修复：把 Ctrl+C / X / A / V 从"命令路由"改为在 PreviewKeyDown 里直接处理； PreviewExecuted 仅保留 Paste / SelectAll / Delete（及兼容右键菜单的 Copy/Cut 分支）作为兜底。

端到端验证（10 项断言全通过）：

用例 内容 结果
F1 单行内拖选 → Ctrl+C PASS
F2 拖选 3 行 → Ctrl+C，剪贴板 3 行齐全 PASS
F3 拖选 4 行 → Ctrl+X，剪贴板齐全 且源行减少 PASS
F4 Ctrl+A → Ctrl+C，全部行在剪贴板 PASS
F5 Ctrl+A → Ctrl+X → Ctrl+Z 撤销 → Ctrl+Y 重做 PASS

并验证待办行整行选中时前缀正确带出：- [x] 已完成事项 / - [ ] 未完成事项； Ctrl+Z / Ctrl+Y 未受影响。

25.3 界面美化

本轮的视觉改动遵循 §2 的「色彩自洽」原则 —— 凡长在便签上的元素，颜色都应当能从这张便签自己身上找到出处。

25.3.1 待办复选框改为自绘样式

  • 优化前：系统默认 CheckBox —— 灰色方框、方形（与 4px 圆角体系不符）、点击区域过小
  • 优化后：TodoCheckBoxStyle 自绘，14×14、4px 圆角、描边 1.3px
    • 描边与填充自动取所属便签的 NoteForeground，因此 12 种配色下都能自然融合
    • 未完成态：透明底 + 同色描边；完成态：实心填充 + 白色对勾
    • 悬停（未完成）：底色 #14000000 给出可点提示
    • 命中区域向外扩 4px（外层 Grid Margin="-4"），解决 14px 太小不好点的问题

25.3.2 完成态改为「只淡文字 + 删除线」

  • 优化前：完成态把整行都调淡，复选框也跟着淡 → 用户难以区分"已完成"和"未完成"
  • 优化后：只让文字变淡 + 加删除线，复选框保持清晰

25.3.3 正文行高由 ~1.35 提到 1.5

  • 效果：多行正文呼吸感更好，长文本阅读不挤
  • 实现：NoteLineHeight => Math.Round(NoteFontSize * 1.5, 2)， 便签窗口与主页编辑区共用同一份计算，避免同一张便签在两处显示时行距不一致

⚠️ 两个实现陷阱： ① LineHeight 是 TextBlock 的属性，TextBox 没有 —— 必须写成附加属性 TextBlock.LineHeight，并设 TextBlock.LineStackingStrategy="BlockLineHeight" 才能生效。 ② XML 注释不能插在标签的属性列表中间（会编译报错）。

25.3.4 色板由 6 色扩展到 12 色

  • 优化前：6 色（米黄 / 薄荷绿 / 雾霾蓝 / 豆沙粉 / 薰衣紫 / 高级灰）
  • 优化后：6 色相 × 深浅两档 = 12 色，深浅用于表达"轻重"——同色相下浅档更退让 （适合背景 / 次要便签），深档更有存在感（适合需要被注意的便签）
  • 命名：色相名 + Deep/Light（如 YellowDeep / YellowLight）
  • 实现要点：
    • 每个色相必须齐备 5 个资源键（Bg / Title / Border / Text / Shadow），共 60 个
    • 深档沿用原 6 色的色值，所以视觉上老用户无感，纯增量
    • 色板列表集中在 NoteColorHelper.All 一处维护
    • 读取必须走 NoteColorHelper.Parse()（内含旧名映射 Yellow → YellowDeep 等 + 兜底默认）， 不要直接 Enum.Parse<NoteColor>

25.3.5 阴影由纯黑改为跟随便签色相

  • 优化前：纯黑阴影，压在彩色纸上会让边缘发脏灰
  • 优化后：Note{色相}{档位}_Shadow 暖色阴影，让便签"落"在桌面上而不是"贴"在上面

25.3.6 折叠态加颜色信息

  • 问题：折叠成胶囊后底色被标题栏色取代，便签"是什么颜色"的信息会丢失
  • 方案：左侧加一道 3px 语义色脊（NoteAccentBrush = Border 色）， 既守住颜色身份，又像"书脊"一样暗示"这是一张便签"
  • 细节：用 Border 色而不是 Bg 色 —— 折叠胶囊底色已经是标题栏色， 若色脊再用 Bg 色会出现色差、显得脏；展开态不需要（那时四周都有便签底色），故仅折叠时可见

25.3.7 锁定态设计化

  • 优化前：锁定后用户分不清"被锁住了"和"界面坏了"
  • 优化后：斜纹浓度定在 7%（3% 时肉眼几乎不可见），并同时给出 「可读的说明 + 可退出的入口」（提示条 + 解锁按钮）

25.3.8 便签纸张质感（本轮最大的视觉改动）

问题：便签是纯色块，视觉上接近"塑料卡片"，和"信件 / 便条纸"的产品意象有距离。

方案：在便签底层叠三层纯绘制的质感：

画刷 作用
PaperFiberBrush 极淡的纸纤维颗粒（不规则短划线平铺）
PaperLightBrush 顶部光照渐变（模拟光源在上方）
纸边厚度渐变 纸边厚度感

三层全部是半透明叠加，因此能跟 12 种便签底色自然融合，不需要为每种颜色各配一套纹理。

工艺上刻意避开了系统材质（Mica / Acrylic）：便签窗口用了透明分层窗口， 与系统窗口背景材质在实现上互斥，且系统材质在 Windows 10 上不可用。 纯绘制方案在 Win10 / Win11 表现一致，也没有窗口样式兼容风险。

⚠️ 本轮最大的技术教训：小尺寸 tile 会产生可见网格。

早先试过 6×6 的 tile，肉眼能看到规则网格，像"布纹 / 网纱"而不是纸。 改为 24×24 tile + 短划线全部偏离网格交点 + 三档浓度（#08 / #0A / #0C）互相错开 后解决。

量化定位过程（水平自相关测周期性）：

6×6 tile   → 自相关在 lag=18（即 6 的整数倍）出现 0.98 的强峰
24×24 tile → 自相关峰值 lag=2 → 0.81，之后平滑衰减，无次级峰

结论：纹理类视觉参数不要靠肉眼判断。 用自相关函数测周期性（有无次级峰）， 用亮度标准差测强度（会不会太脏），一次就能定位。

强度基线：亮度极差 6~7（量程 255）、sd ≈ 0.9 —— 正常距离下只表现为"纸面不光滑"，看清了就说明做脏了。

纤维只画 1.5% 左右的黑，密度刻意做得很低。

  • 导入坐标策略：导入的便签自动摆在屏幕内，不照搬文件里记录的老坐标——一张落在屏幕外的便签「看不见也拖不回来」，表象与导入失败一模一样，极难排查。导入是原子操作，中途出错不留「导了一半」状态，碰到的问题如实列出。
  • 筛选：FilterOption 支持按颜色 / 标签 / 时间范围组合筛选；筛选按钮在搜索框右侧，有筛选生效时亮一个小圆点（防「开着筛选以为便签丢了」），数量联动，一键清除。
  • 搜索关键词高亮：HighlightTextBlock + HighlightSegmenter 在标题与摘要中给命中部分加柔和黄底；高亮分词与「有没有搜到」用同一套判定规则，不会出现「搜到了却没标出」的自相矛盾。

修复

  • 回收站保留天数从没生效过：data.retain_days 滑块能调能存，但程序里没有一处读它。现在每次启动按设定天数清理一次，未到期不动，清理前有提示。
  • 备份改用 VACUUM INTO 一致性快照：原先直接复制数据库文件，数据库在用时拷贝可能拿到「一半新、一半旧」的库——文件大小正常、也能打开，要到恢复那天才发现不能用。快照由 SQLite 原子生成，从根上排除这种损坏。
  • 恢复流程重做：先校验备份文件本身（不合格直接中止，不拿坏文件盖好数据）→ 等所有写入方停止、程序退出过程中替换（含清连接池、删 -wal / -shm）→ 自动重新打开。恢复前必先把当前数据留一份。

26.2 v1.3.0（2026-09-26）：图片附件

  • 添加方式：「更多」菜单 →「添加图片」（可多选）；或编辑区 Ctrl+V 直接粘贴剪贴板图片（顺带修复了此前粘贴图片「按了没反应」——旧逻辑只走文字粘贴通道，非文字剪贴板静默失败）。
  • 展示：缩略图条夹在标题与正文之间，无图时整条不占位；缩略图按显示尺寸解码（DecodePixelWidth），不为小图读整张原图。独立便签窗口与主页编辑区用同一套 AttachmentCollection，不会「便签里有、主界面看不到」。
  • 存储取舍：图片字节直接入库（BLOB）而非外部文件夹，理由见 §8.2 Attachments 表注——备份快照天然包含图片。写入前等比缩小（长边 ≤1600px，ImageSizing）控制体积。

26.3 v1.4.0 / v1.4.1（2026-09-26）：贴边收纳

  • 功能：便签拖到屏幕最左 / 最右边缘松手，贴边收成留 5px 细边的收纳态；鼠标移过去滑出，移开约半秒自动收回。收起绝不把便签整个推出屏幕外——推出去就再也碰不到，只能觉得「便签被弄丢了」。
  • 默认关闭：自动隐藏会改变窗口行为（便签「自己不见了」），对用惯的人容易被当成故障，所以宁可多一步手动打开。
  • 状态记忆：贴边方向存 DockEdge（0=无 1=左 2=右），重启后对着原来的边，但一定展开着——开机就见便签消失比「没贴好」严重得多。
  • v1.4.1 修正：
    • 拖到边缘本身即是意图——拖到边上就贴并记下开关，不再要求先去「更多」菜单开功能（v1.4.0 的开关藏在菜单里，没开时拖到边缘毫无反应，用户只会觉得「坏了」）。
    • 吸附距离 16→28px、唤醒区 20→36px：窗口外有一圈阴影边距，用户眼里的「挨着边」和程序算的边本来就差一点，门槛卡在最边就只能反复试。
    • 拖动靠近边缘时亮琥珀色预览竖条提示「松手贴到左边 / 右边」。
    • 窗口比屏幕宽、两边都够近时改选更近的一边（原先总往左）。
  • 实现要点：DockGeometry 纯函数（常量 SnapDistance=28 / VisibleStrip=5 / ShadowMargin=12，不可混用）+ DockController；动画 Stop + 手动终值 + 防重入；DockControllerTests.cs 提供进程内 STA 测试模板。

26.4 v1.5.0（2026-09-27）：编辑器 ViewModel 收口

  • 没有任何用户可见的变化——这一版把桌面便签窗口与主页编辑区两处几乎相同的编辑逻辑收拢到基类 NoteEditorViewModelBase。两份重复代码的真代价是：每修一个地方都得记得修两遍。
  • 起因 bug：给桌面便签的待办复选框加着色时忘了同步主页编辑区，右侧编辑区的复选框整个消失——看起来完全像样式表问题，实际是两份代码漂移。
  • 颜色兜底：NoteColorConverter 失败时返回全透明，阴影 / 文字色「取到就用、取不到就当透明」的结果是整片看不见。现改为取不到就回退深色（阴影、NoteForeground 均带 FallbackValue）——宁可颜色不准，不让元素隐身。判有效色必须 Color.A > 0。

26.5 v1.5.1（2026-09-27）：卷角

  • 功能：便签右下角可折起一小块（22×22，最上层，IsHitTestVisible=False），纯装饰不承担功能；默认关闭，右键菜单勾选，按便签记忆（IsDogEar 列）。
  • 配色自洽：DogEarPalette 从便签底色推导——亮面 = 底色提亮三成，折痕 = 压暗两成，色相不变；推导失败回退 #F3F0EA，绝不返回全透明。
  • 连带调整：底部相对时间（「刚刚」）从右下移到左下与字数并排（原位置与折角相撞）；内容区留出折角宽度的底部空隙。

26.6 v1.5.2（2026-09-27）：极简模式右键修复

  • 现象：极简模式下右键弹出的是只有「剪切 / 复制 / 粘贴」的小菜单——没有极简模式开关，而极简态没有标题栏没有按钮，人被困在便签里（应急出路：双击进编辑，或从主界面列表改回）。
  • 根因：便签正文每行是一个 TextBox，输入框自带上下文菜单；它在弹菜单前已把 ContextMenuOpening 标记为已处理（e.Handled = true），而自定义逻辑是普通订阅，收不到已处理的事件，全程没被叫醒。
  • 修法：改用 AddHandler(ContextMenuOpeningEvent, handler, handledEventsToo: true)——即便已处理也通知我。极简时弹完整菜单；非极简时仍是原生小菜单，行为不变。

26.7 v1.5.3（2026-09-27）：形态规则、设置窗口与附件管理

  • 极简模式缩放修复：极简窗框残留了折叠态的「不可缩放」设置，把便签从极简拉回原大小后边角拽不动。现在折叠、极简、寻常三种形态各守各的规矩：极简 = 常规外框同尺寸是正确的；折叠不可缩放。
  • 设置窗口自绘标题栏：与主界面同一副手工窗框（CaptionHeight=40），应用名上窗框顶；自绘标题栏下按钮需 IsHitTestVisibleInChrome=True。设置窗口左下角版本号与主页一致。
  • 图片附件管理页（设置 → 数据）：GetStorageSummary 报总数与占用，DeleteOrphans 清理「彻底失去关联」的图片。软删除 ≠ 孤儿——回收站里的便签图片仍有主，不会被清。
  • 主页悬浮按钮调整：悬浮按钮不再压住摘要文字（置顶 / 删除在右侧编辑窗口都有，不重复摆两份）。
  • 双击崩溃修复（真虫子）：主页双击便签标题 / 摘要崩溃，日志有五次记录。根因：TextBlock 带 Inlines（搜索高亮）时 e.OriginalSource 是 Run（FrameworkContentElement，不是 Visual），裸调 VisualTreeHelper.GetParent(Run) 抛 InvalidOperationException。修法：新增 Helpers/TreeWalker.cs（GetParentSafe 对 fce 走逻辑树 fce.Parent，其余走视觉树），全项目 6 处爬树调用点统一收口，禁止再加裸调。
  • 代码整理：NoteWindow 按职责拆 5 个 partial（Menus / DragResize / Reminders / LineEditing / DisplayMode），各有「改前必读」注释。
